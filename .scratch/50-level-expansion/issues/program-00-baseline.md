# 00：50 关扩展基线与章节验收协议

**目标**：冻结 50 关计划的编号、章节、Boss、玩法递进、剧情连续性、性能预算和证据格式，让后续关卡工单可以独立实现又不会破坏产品边界。

**Blocked by**：无

**Status**：ready

## 交付内容

- 在 `PRD.md`、`TECH_DESIGN.md`、`GAME_DESIGN.md` 中记录至少 50 关、10 个章节 Boss、每关新增玩法和剧情节点。
- 定义 `LevelDefinition`/等价数据契约：关卡 ID、章节、长度、节奏 beat、检查点、玩法规则、敌人池、补给、Boss、剧情 cue、资源键和低性能降级。
- 固定 50 关的解锁、存档、继续游戏、章节重试和 Boss 结算规则；坏档必须回退到安全默认值。
- 定义章节交付门槛：每 5 关一组，前 4 关可独立通关，第 5 关 Boss 击破后才解锁下一章。
- 定义每关证据模板，至少包含冷启动入口、完整路线、关键玩法、死亡/重试、离线、后台、低性能、APK 哈希和已知限制。

## 约束

- 固定步长推进所有计时、冷却、预警和 Boss 阶段；`onDraw` 不修改状态。
- 继续使用 Kotlin + Canvas 和本地 `AssetRepository`，不引入未记录的引擎、后端或网络资源。
- 每关至少有一个首次出现的玩法变化和一个新的剧情信息；玩法变化不能只换颜色或增加敌人数。
- 每个高伤害攻击在命中前提供至少 0.25 秒视觉/音频预警。

## 验收标准

- [ ] 50 个关卡 ID 连续、唯一，章节 Boss 位于 05/10/15/20/25/30/35/40/45/50。
- [ ] 每个关卡工单都能从本工单的编号定位到目标、依赖、资源、验收和证据目录。
- [ ] 章节解锁、检查点、重试和结算的状态转移有静态检查和至少一条设备路线证据。
- [ ] 50 关总资源预算、单关内存上限、低性能降级规则和离线包体策略已记录。
- [ ] 任一关卡失败能单独回滚，不要求重置其它已通过章节。
